# Local load check — 2026-09-25

This is a local smoke and load check. It does not establish Hostinger VPS capacity.
The Hostinger panel showed the KVM 4 VPS as expired on 2026-09-23, and the public
`/healthz/` endpoint did not respond during this check.

## Setup

- Windows development machine with 8 GB RAM; Docker Desktop WSL engine limited
  containers to 3.68 GiB.
- Isolated Docker Compose project with PostgreSQL 17, Redis 8, Gunicorn (4 workers,
  2 threads each), Celery worker and beat, and Nginx 1.28.
- Fresh PostgreSQL database seeded with 8 users, 20 products, 7 orders, and
  related demo data. API response caching was disabled, as in `compose.yaml`.
- The read tests used one seeded client token. Tests directly against Gunicorn
  bypassed Nginx. All requests were GETs.

During the sustained products check, a `docker stats` sample showed roughly
403% CPU for Django and 120% for PostgreSQL. The local machine was CPU bound;
the short tests also show warmup and scheduling variation. The Nginx 429s are
expected from its per-IP rate limit and do not represent an application error.

Nginx configuration passed `nginx -t`; all six runtime containers were healthy.
The full backend test suite passed 700 tests, and Ruff and migration checks
passed. The Docker image excluded local database backups and environment files.

## Limitations and next check

The seed dataset is small, all authenticated traffic used one account, and the
load generator shared the same computer as the containers. This check contains
no write flow, image upload, external push/email delivery, or Cloudflare traffic.
After the VPS is available, run `tools/load_smoke.py` against the deployed API
with representative accounts and data while watching CPU, memory, PostgreSQL
connections, Celery queue depth, 5xx/429 rates, and request latency. Ramp traffic
gradually; do not infer a supported user count from this local run.
